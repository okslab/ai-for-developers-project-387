# Task: Frontend Pages for the Appointment Booking API

## Goal

Build the frontend of the Appointment Booking application (Calendly-like, single owner,
anonymous guests) as a **separate, self-contained app** in a new `frontend/` directory.

The interface must:

- obtain **all** data and perform **all** actions **only** through the API described by the
  contract (`contract/openapi/openapi.yaml`);
- work correctly against a **separately running backend** that implements that contract;
- be driven during development by a **Prism** mock server started from the same contract.

The frontend must not contain any mock data, hardcoded records, or direct database/backend
logic. The contract is the single source of truth for both data and behaviour.

## Reference materials

| File | Role |
|------|------|
| `spec.md` | Source of truth for **behaviour**: roles, scenarios, occupancy rule, 14-day booking window. |
| `contract/openapi/openapi.yaml` | The **API contract** the frontend implements against (generated from TypeSpec; checked in). Do not edit — regenerate via `contract/` if the contract changes. |
| `contract/*.tsp` | TypeSpec sources of the contract (read-only reference). |

## Mandatory tech stack

- **TypeScript + Vite** (React).
- **shadcn/ui** + **Tailwind CSS** for UI components.
- **react-router-dom** for client-side routing.
- **openapi-typescript** + **openapi-fetch**: generate a typed API client from
  `contract/openapi/openapi.yaml`.
- **Stoplight Prism CLI** (`@stoplight/prism-cli`) for the contract mock server during
  development.

Use current stable versions. Do not add other large frameworks (no Redux-style stores, no
CSS-in-JS framework) unless a specific need is justified in the implementation notes.

## API access rules

- All data access happens through the generated client via a thin `apiClient` wrapper in
  `src/api/`. **No `fetch` calls and no hardcoded data inside components or pages.**
- The base URL is resolved from the `VITE_API_BASE_URL` environment variable, with a
  sensible default (`http://localhost:4010` — the Prism mock). The contract declares an
  **empty** server URL (`servers: [{ url: "" }]`), so the frontend must not try to read the
  base URL from the spec — it comes from configuration.
- The app must work against a real backend by simply pointing `VITE_API_BASE_URL` at it;
  no code changes allowed.

## Development workflow

1. Start the contract mock:
   `npm run mock` → `npx @stoplight/prism-cli mock ../contract/openapi/openapi.yaml`
   (Prism serves on `http://localhost:4010` by default).
2. Start the frontend pointing at the mock:
   `VITE_API_BASE_URL=http://localhost:4010 npm run dev`.
3. Prism generates response data from the contract schemas for the happy paths. To preview
   error-state UI, run the mock with `--errors` (Prism then serves the error responses
   defined for the operation). Note that with Prism the `409` (slot conflict) and `404`
   (unknown event type) responses are not routed per-request — verify those states against a
   real backend.
4. To verify against a real backend: start the separately running backend serving the same
   contract, then run `VITE_API_BASE_URL=http://localhost:<backend-port> npm run dev`.
   The full flows must work unchanged (see Acceptance criteria).

## Pages and behaviour

Behaviour below follows `spec.md`; wire formats follow `contract/openapi/openapi.yaml`.

### Guest area (public)

#### `/` — Booking-kinds page (spec FR-3)

- Load `EventTypes_list` (`GET /event-types`).
- For each event type show: `name`, `description`, `durationMinutes`.
- Each card links to `/event-types/{id}` (its slots calendar).
- Empty state when the list is empty; loading and error states.

#### `/event-types/:eventTypeId` — Slots calendar + booking form (spec FR-4, FR-5)

- Load the event type via `EventTypes_get` (`GET /event-types/{eventTypeId}`); on
  `NOT_FOUND` show “Event type not found”.
- Load free slots via `Guest_listSlots` (`GET /event-types/{eventTypeId}/slots`) for the
  14-day booking window (omit `from`/`to` so the server uses its defaults).
- Render the returned `Slot[]` grouped by day and time (the server decides availability and
  30-minute grid semantics — the frontend only displays the slots).
- Selecting a slot reveals a booking form: **guest name** and **guest email** (required,
  email format validated). Submitting calls `Bookings_create`
  (`POST /bookings` with `eventTypeId`, `startsAt`, `guestName`, `guestEmail`).
  - `201` → confirmation view with the created booking details (times, guest, event type).
  - `409` (`code: "CONFLICT"`) → “This time has just been taken — please pick another
    slot”, then refresh the slot list.
  - `404` (`code: "NOT_FOUND"`) → event type no longer available.
  - `422` / other validation errors → show the API error message (validation surface).
- Empty-slots state: “No free slots in the next 14 days.”
- Slot times are ISO 8601 UTC; display them in the user’s local timezone (see
  “Date/time handling”).

### Owner area (`/owner`) — fixed owner profile, no authentication

#### `/owner` — Event types admin (spec FR-1)

- List event types via `OwnerEventTypes_list` (`GET /owner/event-types`).
- Create form: `name`, `description`, `durationMinutes` (positive integer). Submit calls
  `OwnerEventTypes_create` (`POST /owner/event-types`). After success, refresh the list
  and clear the form. Surface API errors (e.g. `422`) to the user.

#### `/owner/bookings` — Upcoming meetings (spec FR-2)

- Load `Owner_listUpcoming` (`GET /owner/bookings`). The server already returns only
  bookings with `endsAt >= now`, enriched with `eventTypeName` / `eventTypeDescription`.
- Display each meeting: event type name (+ description), start/end times, guest name and
  email. Empty state when there are no upcoming meetings.

### Navigation

- Top-level navigation between the Guest section (booking kinds) and the Owner section
  (event types, upcoming meetings); the guest section is public, the owner section is
  reachable without login (out of scope: auth).

## UI / UX and error handling

- Every async view has loading, empty, and error states. Errors prefer the API-provided
  `message` where present.
- Map contract error codes to user-facing messages: `CONFLICT` → “slot taken”, `NOT_FOUND`
  → “not found”, otherwise show a generic “something went wrong” plus the message.
- **Date/time handling**: the API returns ISO 8601 UTC (`startsAt`, `endsAt`, `createdAt`).
  Display in the user’s local timezone via `Intl.DateTimeFormat` (locale-aware, includes
  date + time). Do not hand-roll date arithmetic; use the fetched `endsAt` from the API —
  never recompute durations on the client.
- Form validation: name required, email valid, `durationMinutes` a positive integer.
- Keep the design clean and consistent; all components come from shadcn/ui.

## Acceptance criteria (definition of done)

- [ ] `frontend/` is a self-contained Vite + TypeScript + React app; `npm run dev` works.
- [ ] Typed API client is generated from `contract/openapi/openapi.yaml` via an npm script
      and committed.
- [ ] All pages in “Pages and behaviour” are implemented and reachable via routing.
- [ ] No mock data or hardcoded records in components; all data flows through the generated
      client and the contract endpoints.
- [ ] The app runs against **Prism** (`npm run mock` + `npm run dev`).
- [ ] The app runs against a **separately running real backend**: start it, set
      `VITE_API_BASE_URL` to its port — no code changes. The full cross-sectional flow
      succeeds end-to-endвщс: owner creates an event type → it appears in booking kinds →
      guest books a free slot → the booking appears in upcoming meetings.
- [ ] Error surfaces handled: `404` unknown event type, `409` slot conflict, empty slot
      list, empty lists, network/loading failures.
- [ ] `npm run build` (`tsc` + `vite build`) passes without type errors.

## Out of scope (per spec.md)

- Registration, authentication, authorization (the fixed owner profile is assumed).
- Booking cancellation and rescheduling.
- Working-hours / business-hours restrictions on the slot grid.
- Email notifications.
- Multi-calendar or multi-owner support.
- Any changes to `contract/` or `spec.md`.
